# ADR-0002：檢查判定用三值，`known` 與 `fail` 分開

- **狀態**：已接受
- **日期**：2026-09-01
- **決策者**：TerryHC（本輪由 Claude Code 提案並實作）

## Context

`validation.py` 的每一項檢查都在斷言一個會被拿去做決定的主張。寫到第十幾條時撞到一類主張，它們**兩個值都不對**：

- 「ranker 的輸出可以當成互動機率讀」——不成立。實測平均 0.4706 對真實正例率 0.2340。但這是 `class_weight="balanced"` 的**必然結果**，是為了排序品質刻意付的代價。標 `fail` 等於宣稱有東西壞了，會讓真正的紅燈失去意義。
- 「八個特徵都拿到非零權重」——不成立，`editorial quality` 與 `popularity` 係數趨近零。但保留它們是刻意的（便宜、在有真實變異的資料上會有用）。
- 「挑戰者贏過最強的 baseline」——不成立，balanced 輸給 content baseline 0.0223 NDCG。這是產品選擇：拿準確度換 slate 多樣性。

如果只有 `pass`／`fail`，這三條的下場只有兩種：標 `fail` 讓看板長期紅著（於是沒人看紅燈），或**乾脆不寫這條檢查**。

第二種才是真正的風險。一份 100% 全綠的報表，最可能的解釋不是這個系統很完美，是**難堪的檢查沒被寫進去**。

## 選項

| 選項 | 好處 | 代價 | 可逆性 |
|---|---|---|---|
| **A（採用）** 三值：`pass` / `fail` / `known` | 已知限制留在報表上、可被計數、可被 diff；紅燈保持稀有因此有意義 | `known` 可能變成「不想修就標 known」的垃圾桶 | 中——所有檢查、CI、UI 都依賴 |
| B 只有 pass/fail，難堪的主張標 fail | 語意最單純 | 長期紅燈＝沒人看的紅燈；CI 無法用「有 fail 就擋」 | 高 |
| C 只有 pass/fail，難堪的主張不寫 | 看板好看 | 這正是這個 repo 前身犯的錯，見 [L0001](../lessons/0001-generated-docs-endorse-generated-code.md) | 高 |
| D 什麼都不做（沒有檢查套件） | — | 所有主張退回純文字宣稱 | — |

## 決定

我們選 A。三值定義寫死在 `validation.py` 的 module docstring 裡：

```
pass   這一輪主張成立
fail   主張不成立，而且有東西壞了
known  主張不成立，而且原因是刻意的、已記錄的權衡
```

`known` 的存在理由寫在同一段：**讓報表不必在「不誠實的全綠」與「假警報」之間二選一。**

CI 只對 `fail` 擋。`known` 不擋，但它會出現在總數裡（目前 31 項中 4 項），出現在 UI 上，也出現在每個 model manifest 的 `validation` 欄位裡——換句話說**它被計數、被留存、被 diff**。

## 後果

- **好的**：難堪的事實留在最顯眼的地方而不是被刪掉。README 有一整張表在解釋這 4 條為什麼不 pass。model manifest 記下註冊當下的 `known` 數，所以「這一版帶著哪些已知限制上線」是可查的。
- **壞的**：`known` 是一個可以被濫用的出口。防線只有社會性的——`CLAUDE.md` 第 3 條寫明不要把 `known` 改成 `pass`，而新增 `known` 必須同時寫清楚代價。**這條沒有機械化保證，是這個決定最弱的地方。**
- **中性但要知道的**：檢查總數會隨著 `known` 增加而膨脹，「27 pass / 4 known」這個比例本身變成一個要看的數字。比例往 known 傾斜就是設計債在累積。

## 重評觸發

- 當 `known` 超過總數的 25%（目前 4/31 ≈ 13%）—— 代表它正在變成垃圾桶，該逐條重審。
- 當出現「`known` 但其實該修」的實例超過一次 —— 需要加一個機械化的到期機制（例如 `known` 必須帶 `review_by` 日期）。
- 當有人為了讓 CI 過而把 `fail` 改成 `known` —— 這個決定就失敗了，該退回 B。

## 證據

| 主張 | 證據等級 | 來源 |
|---|---|---|
| 目前 4 條 `known`，每條都有具體量測值 | 已確認 | 2026-09-01 本機 `python -m signalweave.validation` |
| 三值不會讓 CI 失去把關能力（fail 仍擋） | 已確認 | `train --seed 7` 曾因 1 條 `fail` 被拒絕註冊 |
| `known` 會隨模型版本一起被記錄 | 已確認 | `artifacts/models/*/manifest.json` 的 `validation` 欄位 |
| 「全綠報表通常代表檢查不完整」 | 推論 | 本 repo 前身的實例支持，但 n=1 |
| `known` 不會被濫用 | 未驗證 | 目前只有社會性防線；見「重評觸發」 |
