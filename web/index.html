Data and model checks

Every claim below is recomputed against this running process, not copied from a document. PASS means the claim holds. FAIL means something is wrong. KNOWN means the claim does not hold and the reason is a deliberate trade-off, recorded rather than hidden.

Stages

    Split contract

    60% representation history 20% ranker fit 20% frozen evaluation

    Profiles, popularity, item-item neighbourhoods and the time-decayed trending signal are built from the first window only. The ranker is fit on the second. The gate never touches the third until it scores it. split.chronological_per_user in the checks tab is what would catch a violation.

    Evidence boundary

    This dataset is generated by a simulator whose preference function is known. That makes the contracts testable and the run reproducible, and it also means the metrics describe the simulator, not people. An offline replay cannot answer what a different ranking would have caused, because the log only contains what the old policy showed.

    What would move this past a simulation, in order: logged impressions with the ranker version that produced them, propensity-weighted or randomised exploration data, shadow traffic with latency and feature-parity monitoring, then a pre-registered online experiment.

    Serving

    The API loads a registered model and scores against it. It does not fit one on the request path, and the policy metrics it reports are the ones that model recorded at training time — not a recomputation that happens to run the same code.

    Registered versions

    Each version keeps a manifest recording its data, code and model digests, its environment, its metrics and its check-suite result. Promotion and rollback are the same operation: python -m signalweave.train --promote VERSION.
